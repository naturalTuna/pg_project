================================================================
  3. 구성 요소 설명
================================================================

  ■ PostgreSQL 17
  ─────────────────────────────────────────────────────────────
  역할    : 관계형 데이터베이스 엔진
  설치위치: /postgres/app/ (소스 빌드 설치)
  데이터  : /pgdata/data/
  로그    : /pgdata/log/
  아카이브: /pgbackup/arc/    (Archive 모드 활성화 시)
  백업    : /pgbackup/back/   (pg_basebackup 스크립트)

  주요 설정 파일:
    postgresql.conf   - 메모리, WAL, 로그 등 DB 엔진 파라미터
    pg_hba.conf       - 접속 인증 정책 (IP, 유저, 인증방식)

  Streaming Replication:
    - Primary → Standby 로 WAL 실시간 전송
    - wal_level = replica
    - max_wal_senders = 10
    - max_replication_slots = 10


  ■ Patroni
  ─────────────────────────────────────────────────────────────
  역할    : PostgreSQL HA 에이전트
  설치    : pip3 install patroni[etcd] (Python 패키지)
  설정    : /etc/patroni/patroni.yml
  서비스  : systemd (patroni.service)
  API 포트: 8008

  주요 기능:
  - PostgreSQL 기동/종료/재시작을 직접 관리
    (pg_ctl 을 직접 사용하지 않음)
  - etcd 를 통해 Leader Lock 획득 경쟁
  - Primary 장애 감지 후 Standby 자동 승격
  - 복구된 Primary 를 Standby 로 자동 Rejoin
    (pg_rewind 로 타임라인 차이 자동 복구)
  - Standby 초기 구성 시 pg_basebackup 자동 실행


  ■ etcd
  ─────────────────────────────────────────────────────────────
  역할    : 분산 Key-Value 합의 스토어
  버전    : v3.5.x
  설치위치: /usr/local/bin/etcd, /usr/local/bin/etcdctl
  설정    : /etc/etcd/etcd.conf
  데이터  : /var/lib/etcd/
  서비스  : systemd (etcd.service)
  포트    :
    2379 - 클라이언트 포트 (Patroni → etcd 통신)
    2380 - 피어 포트      (etcd 노드 간 통신)

  노드 구성 (postgresql_install.sh 입력 단계에서 선택):
    1) 단일 노드 : etcd 서버 1대
                   → etcd 서버 장애 시 Patroni 가 Leader Lock 을 갱신 못 해
                     Primary 가 강등되고 failover 도 불가 (SPOF)
    2) 3노드     : etcd 서버 + Primary + Standby 에 etcd 설치 (권장)
                   → 1대 장애에도 quorum(2/3) 유지
                   → patroni.yml etcd3.hosts 에 세 노드 모두 등록
                   → 세 서버 간 2379 / 2380 포트 허용 필요
    상태 확인:
      etcdctl --endpoints=http://<IP1>:2379,http://<IP2>:2379,http://<IP3>:2379 endpoint health
      etcdctl --endpoints=http://<IP1>:2379 member list

  주요 기능:
  - Patroni Leader Lock 보관
    (누가 현재 Primary 인지 저장)
  - TTL 만료 시 Leader 교체 허용
  - Split-brain 방지
    (etcd quorum 없이는 승격 불가)

  TTL 설정 (patroni.yml 기준):
    ttl: 30           - Leader Lock 유지 시간 (초)
    loop_wait: 10     - Patroni 헬스체크 간격 (초)
    retry_timeout: 10 - 재시도 타임아웃 (초)


================================================================
  4. 데이터 흐름
================================================================

  ■ 정상 운영 시
  ─────────────────────────────────────────────────────────────

  [Write 요청]
    APP → Primary:5432 → PostgreSQL → WAL 생성
                                       │
                                       ▼
                              Standby WAL 수신 → 반영

  [Leader Lock]
    Primary Patroni ──갱신(10초마다)──► etcd Leader Lock


  ■ Failover 발생 시 (Primary 장애)
  ─────────────────────────────────────────────────────────────

  1. Primary 서버 다운
  2. etcd 의 Leader Lock TTL 만료 (약 30초)
  3. Standby Patroni 가 etcd에서 Leader Lock 획득
  4. Standby Patroni 가 pg_ctl promote 실행
  5. Standby → 새 Primary 승격
  6. APP 재접속 → 새 Primary:5432

  ■ 구 Primary 복구 후 Rejoin
  ─────────────────────────────────────────────────────────────

  1. 구 Primary 서버 기동
  2. Patroni 가 자동으로 현재 Primary 확인
  3. pg_rewind 로 타임라인 차이 복구
  4. 자동으로 새 Primary 의 Standby 로 편입
  5. Streaming Replication 재개


================================================================
  5. Failover / Switchover 동작
================================================================

  ■ Failover (비계획 장애)
  ─────────────────────────────────────────────────────────────
  - Primary 장애 자동 감지 → 자동 승격
  - 소요 시간: 약 30~60초 (TTL + 승격 시간)
  - 데이터 손실: maximum_lag_on_failover 설정 이내
    (기본: 1MB. 이 이상 뒤처진 Standby는 승격 후보에서 제외)
  - 수동 개입 불필요

  ■ Switchover (계획된 전환)
  ─────────────────────────────────────────────────────────────
  - 무중단 역할 전환 (점검, 업그레이드 등)
  - Primary 데이터를 Standby 와 동기화 후 전환
  - 데이터 손실 없음

  실행 명령어:
    patronictl -c /etc/patroni/patroni.yml \
        switchover pg-cluster

================================================================
  ■ 참고: postgresql.conf 주요 파라미터 (HA 모드)
================================================================

  # 접속
  max_connections     = 150        (기본값)

  # 메모리 (서버 리소스 기반 자동 계산)
  shared_buffers      = 메모리의 1/4
  effective_cache_size= 메모리의 3/4
  work_mem            = (메모리/4) / max_connections
  maintenance_work_mem= 메모리의 1/20

  # WAL (서버 메모리 기반 자동 계산)
  wal_level           = replica
  min_wal_size        = 메모리(GB) × 64MB  (최소 256MB)
  max_wal_size        = 메모리(GB) × 256MB (최소 1024MB)
  wal_keep_size       = max_wal_size의 절반
  max_wal_senders     = 10
  max_replication_slots = 10

  # 로그
  log_statement       = ddl
  log_filename        = postgresql-%Y-%m-%d.log
  log_min_duration_statement = 1000  (1초 이상 쿼리 기록)

================================================================
  부록. HA 에서 백업 복구 (pitr_restore.sh)
================================================================

  pitr_restore.sh 는 Patroni 가 떠 있으면 실행을 막는다. HA 는 아래 순서로 복구:

  1) 자동 failover 중지
       patronictl -c /etc/patroni/patroni.yml pause
  2) 모든 DB 노드에서 Patroni 중지 (PostgreSQL 도 같이 내려감)
       sudo systemctl stop patroni
  3) 복구할 노드(보통 기존 Primary)에서
       bash <엔진경로>/etc/backup/pitr_restore.sh [--target-time "YYYY-MM-DD HH:MM:SS"]
     ※ 백업은 백업 서버에, 아카이브는 Primary 에 있으므로 백업 디렉토리를
        복구 노드로 먼저 복사해야 할 수 있다 (BACK_PATH 와 같은 경로로)
  4) 복구 확인 후 PostgreSQL 중지 → Patroni 기동 → resume
       <엔진경로>/bin/pg_ctl -D <DATA> stop -m fast
       sudo systemctl start patroni
       patronictl -c /etc/patroni/patroni.yml resume
  5) Standby 를 새 Primary 기준으로 다시 복제
       patronictl -c /etc/patroni/patroni.yml reinit <클러스터명> <standby 이름>

  WAL 아카이브 정리 (wal_cleanup.sh) 는 Primary / Standby 양쪽 크론에 등록돼 있다.
  백업이 없는 노드는 "보관 개수 × 백업 주기 + 1" 일 지난 WAL 을 지운다.



================================================================
  부록. VIP (Primary 를 따라 이동)
================================================================

  설치 시 VIP 를 선택하면 두 단계로 VIP 를 관리한다.

  1) 즉시 반응: Patroni callback
       patroni.yml → postgresql.callbacks.{on_start,on_stop,on_restart,on_role_change}
       = <엔진경로>/etc/patroni/vip_callback.sh <action> <role> <scope>
       role 이 primary(master) → ip addr add VIP + arping -U (스위치/클라이언트 ARP 갱신)
       그 외 / on_stop → ip addr del VIP

  2) 보정: vip_check.sh (실행 계정 crontab 매분, 20초 간격 3회)
       curl http://<노드>:8008/primary
         200 → VIP 없으면 추가
         503 → VIP 있으면 제거
         무응답 → 2회 연속이면 제거 (Patroni 가 죽어 상대 노드가 승격하는 경우 중복 방지)

  확인 / 수동 조치
       ip -o -4 addr show | grep pgvip            # 현재 노드에 VIP 가 있는지
       tail -f <로그경로>/vip.log                  # 추가/제거 이력
       bash <엔진경로>/etc/patroni/vip_check.sh --once   # 즉시 보정 1회

  switchover 시 흐름
       patronictl switchover → 기존 primary on_role_change(replica) → VIP 제거
                             → 새 primary on_role_change(primary) → VIP 추가 + GARP
       앱은 재접속만 하면 같은 VIP 로 새 primary 에 붙는다.

  주의
       - 같은 L2 서브넷 전제. 클라우드는 LB / DNS 사용.
       - 고립된 노드는 스스로 VIP 를 못 내릴 수 있다 → 완전한 펜싱은 watchdog 추가 검토.
       - VIP 를 다른 장비가 이미 쓰고 있으면 IP 충돌 → 설치 pre-flight 에서 ping 으로 경고.
