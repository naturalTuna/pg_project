1. 한눈에 보기

인터넷이 되는 서버에서 설치에 필요한 모든 것을 postgresql/ 한 디렉토리로 모으고, 그걸 폐쇄망으로 옮겨 소스 빌드 → initdb → 튜닝 → 백업 → (HA) Patroni 구성까지 스크립트 한 번으로 끝낸다. 운영은 pgmon(모니터링)과 pg_tune(튜닝)으로.

2. 패키지 (pg_download.sh)

사람이 "PG 몇 버전엔 무슨 rpm" 표를 관리하지 않게, 받은 소스와 GitHub 태그를 보고 자동으로 정한다. 다운로드 서버는 설치 서버와 같은 OS / 메이저 버전이어야 한다 (rpm · python 버전).

3. single 구성

pgmon 저장소 DB 도 이 방식으로 설치한다. HA 라면 보통 etcd 서버에 single 로 하나 두고 pgmon 을 같이 돌린다.

4. HA 구성

3대: etcd 서버(설치 실행 + 감시 + 백업 저장소) · Primary · Standby. Patroni 가 PG 기동 / 승격 / 복제를 관리하고, etcd 의 leader key 로 "누가 Primary 인가" 를 하나로 정한다. 앱은 VIP 하나만 안다.

서버설치 / 실행되는 것죽으면
PrimaryPostgreSQL, Patroni(systemd), VIP 스크립트(callback + cron), softdog, pgBackRest(archive-push), (3-node) etcd약 30~40초 뒤 Standby 자동 승격 + VIP 이동
StandbyPrimary 와 동일 (Patroni 가 pg_basebackup 으로 클론)복제만 끊김, 서비스 계속. 살아나면 자동 재합류
etcd 서버etcd, vip_watch(감시·알림), pgBackRest 저장소 + 백업 크론, pgmon (+ 저장소 DB single)3-node etcd 면 영향 없음 / 1-node 면 failsafe_mode 로 Primary 유지(그동안 failover 불가). 감시·백업만 멈춤

5. HA 설치 흐름

etcd 서버에서 bash postgresql_install.sh → ha. 빌드는 etcd 서버에서 한 번만 하고 SSH/scp 로 배포한다.

7. 안전장치 (split-brain / 유실 방지)

Patroni 만으로는 "멈춘 Primary 가 나중에 깨어나는" 경우를 막지 못한다. 그래서 세 가지를 설치 단계에서 같이 켠다 (입력으로 선택).

8. VIP 3중 관리

Primary 를 따라 이동하는 가상 IP. 같은 L2 서브넷 전제 (클라우드는 LB / DNS). 즉시 반응(callback) → 놓친 것 보정(vip_check) → 바깥에서 감시(vip_watch) 순으로 겹쳐 둔다.

9. 백업 — basebackup vs pgBackRest

설치 때 백업 선택 (pgbackrest / basebackup) → Archive → Backup 순으로 묻는다. HA 에서 pgBackRest 를 고르면 etcd 서버가 저장소가 되어 공유 스토리지 없이도 failover 와 무관하게 WAL 이 이어진다.

basebackuppgBackRest
백업 종류매번 전체 (tar.gz)full / diff / incr, 압축(lz4), 병렬
보관 정리BACKUP_KEEP 개수 + wal_cleanup.shrepo1-retention-full (expire 자동)
기본 크론매일 02:00일요일 02:00 full + 월~토 diff
복구pitr_restore.shpgbr_restore.sh (--target-time / --set / --delta)
HA 저장 위치각 DB 노드 (백업은 선택한 노드)etcd 서버 한 곳 (backup-standby=prefer)
추가 준비없음설치 시 소스 빌드(meson), DB 노드 → etcd 서버 SSH 키 (자동 등록)

HA 의 archive_mode / archive_command 는 patroni.yml DCS 파라미터에 들어가 첫 기동부터 동작한다. pgBackRest 면 Standby 의 restore_command 도 저장소의 archive-get.

10. 노드 추가 / DR

etcd 서버에서 bash add_node.sh. 새 서버는 계정·sudo·디렉토리·/etc/hosts·SSH 키만 준비하고 PG 는 설치하지 않는다.

11. 모니터링 — pgmon

psql + bash 만으로 동작하는 터미널 모니터링. 수집은 DB 별 collector 프로세스가 하고(root 불필요), 데이터는 저장소 DB pgmon 에 쌓는다.

12. 쿼리 튜닝 — pg_tune

AI 없이 규칙 진단 + 실제 검증. pgmon Statement 화면에서 t → 번호로 바로 실행하거나 CLI 로 쓴다.

진단 규칙 (예)조치 방향
대부분 버리는 Seq Scan / 인덱스 후 Filter 로 대부분 버림단일 · 복합 인덱스 후보 (hypopg 로 검증)
LIMIT 때문에 전체 정렬 (Gather Merge 포함)(= 컬럼 + 정렬 컬럼) 복합 인덱스
Nested Loop 수천 회 반복 / 상관 서브쿼리조인 키 인덱스, Hash/Merge Join 실험, JOIN/EXISTS 재작성
컬럼에 함수 · 캐스트 · LIKE '%..'범위 조건 재작성, 표현식 인덱스, pg_trgm (해당 컬럼은 인덱스 후보에서 제외)
추정 vs 실제 행수 10배+ANALYZE / CREATE STATISTICS, Rows 힌트 실험
Sort/Hash 디스크 spill, lossy bitmap, JIT 과다work_mem · jit=off 실험 (--analyze)
